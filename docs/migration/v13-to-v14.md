# Migrating from 13.x to 14.0

14.0.0 ("core architecture v2") is a major release. Config schema v12 becomes the runtime schema, feature modules move
to one lifecycle with declared capabilities and per-instance state, and `mcp-gateway config migrate --to v12` writes
files. Authentication, authorization, the proxy layer and the module failure policies are unchanged.

**Short version:** upgrade to 13.9.x first and clear its deprecation warnings, or upgrade straight to 14.0 — your
v11 file keeps loading (migrated in memory, with warnings) until 15.0. Then run
`mcp-gateway config migrate --to v12 --in-place` when convenient.

## 1. Before you upgrade

1. Run 13.9.x and read the deprecation warnings (`mcp-gateway validate -c mcp-gateway.yml` or
   `GET /api/v1/admin/deprecations`). They list the five v11 fields 14.0 renames.
2. Preview the change: `mcp-gateway config diff --to v12 -c mcp-gateway.yml`.
3. Note what reads or writes the config programmatically (Helm values, Terraform, CI scripts, clients of
   `GET`/`PUT /api/v1/admin/config`): they see schema v12 names from 14.0 on (step 4).

## 2. What changes in the config file

| Schema v11 (13.x) | Schema v12 (14.0) |
|---|---|
| `version: 11` | `version: 12` |
| `kernel.modules` | `modules.activation` |
| `kernel.failurePolicy` | `modules.failurePolicy` |
| `features.genaiTelemetry` | `features.genaiOtel` |
| `features.policyShadow` | `features.policySim` |
| `features.postQuantumTls` | `features.pqTls` |
| — | `modules.lifecycle` (`initTimeoutMs`, `unloadTimeoutMs`, `drainMs`) — new |
| — | `modules.capabilities.<module>.deny` — new |

Everything else (servers, auth, store, the body of every feature section) is unchanged. Design:
[docs/design/schema-v12.md](../design/schema-v12.md); inventory: [docs/deprecations.md](../deprecations.md).

How 14.x reads a file:

- `version: 12` — schema v12. The five v11 fields are refused (the error names the v12 field).
- `version: 11` — schema v11, **migrated in memory**: the same runtime config, one `DEPRECATED (removed in 15.0.0)`
  warning per v11 field and one startup notice. Silence the warnings with `MCP_GATEWAY_SILENCE_DEPRECATIONS=all`.
- no `version` — v11 when the file uses a v11-only field, otherwise v12 (both read the same).
- Mixing schemas (`kernel` and `modules`, or `version: 11` with a v12 section name) is refused.

**v11 files are no longer read from 15.0.0.**

## 3. Migrate the file

```bash
# write mcp-gateway.v12.yml next to the file (or -o <path>); the input is not touched
mcp-gateway config migrate --to v12 -c mcp-gateway.yml

# or rewrite the file itself; the original is kept as mcp-gateway.yml.v11.bak
mcp-gateway config migrate --to v12 --in-place -c mcp-gateway.yml
```

YAML comments and layout are kept, the result is validated before anything is written, and an existing output or
backup is never overwritten without `--force`. `--dry-run` only prints the v12 config, a unified diff and the
compatibility report; `--json` for tooling. A file that is already v12 is left alone.

Kubernetes / Helm: update the ConfigMap or the `config:` value the same way (the tool works on any copy of the file).

## 4. Other breaking changes

- **Admin API in v12 form.** `GET /api/v1/admin/config` returns `version: 12`, `modules.*` and the v12 section names;
  config diffs and config-assistant plans use the same form. `PUT` / `POST` bodies may still be
  v11 (migrated in memory).
- **Per-instance module state.** Several `Gateway` instances in one process no longer share module state (approval
  queue, billing meters, GenAI spans, rollouts, budgets, task runs, SCIM directories, journals, …). A module disabled
  by a reload loses its in-memory state; when it is enabled again it starts fresh. State kept in the shared store
  (`store.backend: redis | sqlite | eventlog`) is not affected.
- **Capabilities.** `modules.capabilities.<module>.deny` refuses the activation of a module that declares a denied
  capability; the module's failure policy applies (`closed` for security guards: calls in its scope are refused).
  `GET /api/v1/admin/kernel` lists each module's `capabilities` and `lifecycle` (`v2` or `v11-compat`).
- **Control plane / data planes: upgrade the data planes first.** A 14.0 control plane distributes the config in
  schema v12, which 13.x data planes refuse; 14.x data planes accept both v11 and v12. Roll back in the reverse
  order (control plane first).
- **Lifecycle bounds.** With `modules.lifecycle.initTimeoutMs` / `unloadTimeoutMs` set, a module whose `init` /
  `disable` / `dispose` takes longer is marked failed (start and reloads continue). No bounds are set by default.
- **Messages.** The 404 for an inactive module names `modules.activation` and the v12 section.
- **Embedders / plugin authors.** `FeatureModule` gains `apiVersion: 2` and `capabilities`; `FeatureContext` gains
  `timers`, `net`, `capabilities` and `instanceScope`. Modules without `apiVersion: 2` run unchanged through the
  v11-compat adapter. Module state that must be per gateway: `instanceLocal(moduleId, name, factory)` from
  `kernel/instance`.

## 5. Roll back

14.0 does not change data on disk (stores, audit logs, journals keep their formats), so rolling back is a binary and
config change:

1. If you migrated in place, restore the v11 file: `mcp-gateway config rollback -c mcp-gateway.yml` (restores
   `mcp-gateway.yml.v11.bak`; the v12 file is kept as `mcp-gateway.yml.v12.bak`). Without a backup:
   take the v12 file back by hand with the table in step 2 (rename the keys back, set `version: 11`, drop
   `modules.lifecycle` and `modules.capabilities` — 13.x has no equivalent).
2. Pin the 13.9 line: `npm i @winstonsayno/mcp-gateway@v13-lts` (or `@13.9`), image
   `ghcr.io/harrisoncn/mcp-gateway:13` (or `:13.9.0`), Helm `image.tag: "13"`.
3. Restart. 13.9.x reads the v11 file as it is; it refuses a `version: 12` file.

A v11 file works on both 13.9.x and 14.x, so keeping the v11 file until the 14.0 rollout is complete makes rollback
a binary-only change.

## 6. Support

13.9.x is maintained (security and critical fixes) on branch `lts/13.x`, npm dist-tag `v13-lts`, image `:13` — see
